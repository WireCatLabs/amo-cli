# Working rules for agents

The [WireCat CLI standards](node_modules/@wirecat/cli-base/docs/standards/README.md) apply here and win over this
file and over every other document in this repository. The handbook ships inside `@wirecat/cli-base`; run
`pnpm install` first. Read the page for the area you change before changing it, and cite the rule ids the change
touches (`WC-<AREA>-<n>`) in the commit message and the pull request. The rules of this CLI alone are in
[CLAUDE.md](CLAUDE.md).

## Design

[docs/dev/DESIGN.md](docs/dev/DESIGN.md) holds the owner's answers to the

## How a command reaches the account

<!-- cspell:words gcal SECR -->

The template's `comments` sample is gone: amo's own commands cover each pattern it showed. The parts below are the
template's, kept in amo's own files. [cli-template](https://github.com/WireCatLabs/cli-template/tree/main/src) still
has the sample, for a pattern you want to read in isolation.

Kept from the template, the same for every service:

- **Token storage and the command context**, `src/context.ts`: cli-core's `ProfileTokenStore` keeps the long-lived
  token (`AMO_TOKEN` with `AMO_HOST`, then the keyring, then a private file; a run with moved folders never replaces
  the owner's entry, WC-SECR-4, WC-SECR-24), and `contextOf` takes settings, the keyring and the run from cli-core's
  `baseContext` only. `src/amo/oauth.ts` keeps the integration's tokens through cli-core's oauth module. Every request runs inside its `run()`, which bounds it by
  `--timeout` and records a run named after the command (WC-LIFE-5, WC-LIFE-15).
- **Sign-in**, `src/commands/session.ts`, `src/whoami.ts` and `src/amo/oauth.ts`: `session start | status | end |
  list`. The token is read hidden or from stdin, never as an argument, and checked against the account before it is
  kept with the address and the token's user (WC-ACCT-12, WC-SECR-5). `--client-id` signs in through the integration
  in the browser instead (WC-SECR-22).
- **The setup flow**, `src/setup/`: the questions `amo setup` and WireCat Desktop ask, in English, Russian and
  Spanish, with the same check `session start` runs.
- **Permissions**, `src/config.ts` and `src/api-keys.ts`: the program hands cli-core the whole `configuration`, and
  each command path is its own key (WC-PERM-22). Each API operation has a key from its path and verb, and `api call`
  also checks the key of the command it does the same as, with `alsoChecks`.
- **Writes**, cli-core's shared writes over `src/crm/writer.ts`, and `src/commands/write.ts` for `api call`: the
  guard asks or refuses by the command's key, the send journal records the attempt, the answer carries
  `operation_id`, and a write is tried again only when amoCRM refused its rate: one that got no answer is
  `outcome_unknown` (WC-PERM-13, WC-PERM-17, WC-OUT-10, WC-LIFE-9). `--dry-run` and `AMO_READ_ONLY` are cli-core's.
- **MCP and doctor**, `src/program.ts`: cli-core's `appMcpCommand` and `appDoctorCommand`, with amo's own `name` and
  `untrusted` list (WC-MCP-11).
- **The test harness**, `src/testing/harness.ts`: the CLI through its own `run()`, with a memory keyring and the fake
  account in place of the network (WC-TEST-2, WC-TEST-3, WC-TEST-6).

amoCRM's own:

- **The adapter**, `src/amo/`: `transport.ts` sends the token in a header only, with no redirects, a timeout,
  cli-core's `Pacer` under amoCRM's request limit and cli-base's error codes. It tries a read again on a refused rate
  or a lost answer, and a write only on a refused rate, and refuses a write only an administrator may send
  (WC-SECR-6, WC-SECR-7, WC-OUT-20). `errors.ts` maps amoCRM's refusals, `account.ts` checks an account's address,
  and `routes.ts` names every operation amo's own code calls.
- **The operation table**, `src/amo/operations.ts`: generated by `pnpm kommo:operations` from
  `contracts/kommo-openapi.json`; never edit it by hand. `src/amo/allow-list.ts` adds what amoCRM documents but the
  spec lacks, each entry with its page.
- **The CRM source and writer**, `src/crm/`: `source.ts` reads the account for cli-core's sync and live lists,
  `records.ts` maps amoCRM's records, `activities.ts` reads tasks, notes and calls, and `writer.ts` sends the writes.
  Each field name comes from the amoCRM or Kommo reference or a captured answer, never from memory; no wire type
  leaves them (WC-ARCH-3).
- **The commands**, `src/commands/`: `crm-shared.ts` mounts cli-core's shared CRM commands (`sync`, `deals`,
  `pipelines`, `stages`, `fields`, `activities`, `changes`, and `people`, `organizations` and `users` read live) over
  amo's source and writer. amoCRM has no leads apart from deals, so it mounts no `leads`. amo adds `api` (`api list`,
  `show` and `call`), `session`, `account` and `schedule`.
- **The strict fakes**, `src/testing/fake-amo.ts` and `src/testing/fake-activities.ts`: their routes are the
  operation table and the allow-list, and `spec-check.ts` checks each body and query against the spec's schemas.
  They refuse an unknown path, parameter or field, so a name typed from memory fails a test instead of reaching the
  owner's account.
- **The live check**, `bin/amo-live`: this checkout's build against a real account, read-only by default. With
  `--write` it makes, moves and closes one test deal, and a pass is recorded in `docs/dev/live-checks.txt`, which
  `bin/release` checks.

## Template-owned files

This CLI was made from [cli-template](https://github.com/WireCatLabs/cli-template). `template.json` names the files
`npx @wirecat/cli-template upgrade` keeps in step with the template. Change one of them here only when this CLI needs
to differ; `upgrade` asks before it touches your change. Text that holds for this CLI alone goes into the pages it
owns, such as `DESIGN.md`, `CLAUDE.md` and `README.md`, not into a template-owned page.
